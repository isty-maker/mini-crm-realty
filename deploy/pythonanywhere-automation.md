# Автоматический деплой на PythonAnywhere Free

GitHub Actions использует уже запущенную выделенную Bash-консоль. Ручной запуск с `main` предлагает режимы `dry-run` и `apply`. Для apply оператор вводит полный SHA текущего `main`; workflow требует успешный CI push для этого же SHA. Автоматический запуск выключен по умолчанию. После включения workflow принимает только успешное завершение существующего `CI` для события `push` в `main` этого репозитория. Это включает push, созданный merge PR. Проверки PR сами по себе деплой не запускают. Checkout GitHub Actions и сервер должны подтвердить один и тот же полный SHA. Если `main` успел продвинуться до серверного fetch, устаревший запуск остановится.

## Переход с установленного launcher на v2

Если рабочий сайт уже прошёл apply, reload и ack на `278552f1`, сохраняйте существующие `production`, `last-good`, секрет и переменные. Для перехода используйте первый релиз без миграций. Не объединяйте PR #188 с этим первым этапом.

1. Выключите repository variable `PA_AUTO_DEPLOY` и дождитесь окончания текущего workflow. Проверьте, что `pending` отсутствует, а `last-good` совпадает с рабочим HEAD.
2. После принятия PR этого изменения получите полный SHA принятого релиза из GitHub и дождитесь успешного push-CI. В выделенной Bash-консоли установите v2 из этого коммита, не переключая рабочий checkout. Подставьте проверенный SHA в пример:

   ```bash
   (
     set -euo pipefail
     umask 077
     cd /home/isty/mini-crm-realty
     release='<полный SHA принятого main>'
     [[ $release =~ ^[0-9a-f]{40}$ ]]
     git fetch --no-tags origin refs/heads/main
     test "$(git rev-parse FETCH_HEAD)" = "$release"
     state="$HOME/.mini-crm-deploy"
     test "$(git rev-parse HEAD)" = "$(cat "$state/last-good")"
     test ! -e "$state/pending"
     temp_launcher=$(mktemp "$state/deploy-v2.XXXXXXXX")
     trap 'rm -f -- "$temp_launcher"' EXIT
     git show "$release:deploy/deploy" > "$temp_launcher"
     chmod 700 "$temp_launcher"
     bash -n "$temp_launcher"
     test "$(bash "$temp_launcher" --protocol-version)" = 2
     cmp "$temp_launcher" <(git show "$release:deploy/deploy")
     mv -T "$temp_launcher" "$state/deploy-v2"
   )
   ```

   Workflow обращается к `deploy-v2` и проверяет, что тот отвечает версией протокола `2`. На старом launcher он не запускается. Предыдущий файл `deploy` остаётся отдельно. Не вызывайте его для нового релиза.
3. Запустите ручной `dry-run` с `main` и убедитесь, что в журнале указаны точный SHA, политика `none` и успешное завершение репетиции. Затем запустите ручной `apply` с этим же SHA. Проверьте reload, `/healthz/`, `X-App-Revision` и ack. Убедитесь, что `last-good` обновлён и `pending` исчез. После этого можно включить `PA_AUTO_DEPLOY=true` для будущих релизов.

Проверьте чистый Git, включая неигнорируемые файлы, и origin `https://github.com/isty-maker/mini-crm-realty.git`. При необходимости внесите `/.env`, `/db.sqlite3-wal`, `/db.sqlite3-shm` и `/db.sqlite3-journal` в локальный `.git/info/exclude`. Дополнительные миграции должны пройти согласование, прежде чем дерево можно считать чистым.
3. На вкладке Web проверьте source directory `/home/isty/mini-crm-realty`, virtualenv `/home/isty/mini-crm-realty/venv`, Python 3.12 (наблюдаемая версия 3.12.8) и локальное отображение `/static/` на `/home/isty/mini-crm-realty/staticfiles`. Скрипт допускает обновления патч-версии Python 3.12. Сохраните действующую конфигурацию WSGI и загрузку окружения. В WSGI после настройки пути и окружения импортируйте `from realcrm.wsgi import application`. Этот модуль запоминает SHA при запуске рабочего процесса и отдаёт его в заголовке `X-App-Revision` на `/healthz/`. Сам URL по-прежнему возвращает `ok`.

Для серверных команд нужны `DEBUG=False`, домен в `ALLOWED_HOSTS`, `https://isty.pythonanywhere.com` в `CSRF_TRUSTED_ORIGINS`, действующие переменные `YANDEX_CLIENT_KEY_ID`, `YANDEX_CLIENT_SECRET_KEY`, `YANDEX_STORAGE_BUCKET_NAME` и тот же режим миграций, что у рабочего сайта. Переменные в окружении консоли имеют приоритет над `.env`. Проверьте предупреждения `check --deploy`, включая настройки Django secret key и HTTPS, до включения автоматического режима. Проверки не обращаются к рабочим объектам Yandex.
5. Установите отдельно проверенную копию `deploy/deploy` из принятого коммита в `/home/isty/.mini-crm-deploy/deploy-v2`. Подготовьте файл из проверенного checkout или передайте его через Files. GitHub Actions вызывает только этот установленный launcher. Обновление launcher выполняет оператор после ревью. Инициализируйте `last-good` **только при первоначальной настройке** значением проверенного SHA рабочего сайта. Сверьте его с HEAD. Пример команд для оператора после подготовки файла:

   ```bash
   umask 077
   install -d -m 700 "$HOME/.mini-crm-deploy"
   install -m 700 /path/to/reviewed/deploy "$HOME/.mini-crm-deploy/deploy-v2"
   set -o noclobber
   printf '%s\n' bf6164eb52efacaa8eaaff6174c6e348778db049 > "$HOME/.mini-crm-deploy/last-good"
   set +o noclobber
   ```

6. Откройте выделенную Bash-консоль через Dashboard и оставьте её на свободном приглашении оболочки. Запишите фактический ID. Ранее использовалась консоль `42628336`. После перезапуска проверьте ID заново. Используйте только эту консоль для деплоя. Интерактивная команда, другой shell или длинный prompt могут помешать обмену.
7. Создайте GitHub Environment `production`, ограничьте deployment branches веткой `main`, если настройка доступна, и защитите `main` ревью и обязательным CI. Задайте в environment секрет `PA_API_TOKEN`, variables `PA_USERNAME=isty` и `PA_CONSOLE_ID`. Оставьте **repository variable** `PA_AUTO_DEPLOY` отсутствующей или со значением `false`. С токеном обращайтесь как с учётными данными аккаунта. Клиент передаёт его только официальному API, без HTTP-переадресаций.

## Ручная проверка и включение

- Для `dry-run` и `apply` launcher берёт отдельный online-снимок SQLite в приватном scratch-каталоге. На снимке исполняются допущенные миграции, затем `quick_check`, `foreign_key_check`, проверка пустого плана, Django check и dry-run сборки статики. Dry-run открывает рабочую БД на чтение. Checkout, рабочая схема, reload и `last-good` остаются прежними. Если миграция неизвестна, репетиция остановится и потребует предварительного ревью и SHA-допуска.
- Workflow распознаёт последнее приглашение Bash после удаления ANSI-оформления и нормализации CR/CRLF. При нестандартном prompt в выделенной консоли можно выполнить `PS1='crm-deploy@pythonanywhere:~$ '`. Оставьте консоль свободной и используйте её только для деплоя. Приглашение по выводу API не гарантирует, что никто не начал ввод. При HTTP 412 откройте консоль в браузере и, если команда уже отправлялась, проверьте приватный журнал, блокировку и `pending` перед повтором. POST не повторяется автоматически. Успех подтверждает полная строка с уникальным номером запуска и кодом выхода.
- Для ручного `apply` укажите полный SHA актуального `main` с успешным push-CI. Launcher после репетиции делает **новый** неизменённый SQLite backup, сверяет исходную схему и план в режиме чтения, заново сверяет Git HEAD и tip `main`, сохраняет backup и пишет `pending`. После fast-forward он снова проверяет схему и план перед миграцией. Завершение подтверждается через reload, `/healthz/` с правильным `X-App-Revision` и отдельный ack.
- Держите `AUTO_APPLY_MIGRATIONS` выключенным как в Bash, так и в окружении WSGI. Скрипт прекращает работу при включении этой настройки в его окружении. Рабочий virtualenv он проверяет, но не обновляет. На сервере должно хватать места для архива и SQLite-снимка с журналом. Проверка свободного места использует размер SQLite в страницах, включая WAL, но личная квота PythonAnywhere может быть ниже. При ошибке резервного копирования или репетиции launcher останавливается до изменения рабочего checkout и БД.

## Какие миграции идут автоматически

Автоматический push использует отдельный режим `auto-apply`. Он разрешает пустой план либо одну атомарную миграцию с одной стандартной Django-операцией `CreateModel`. Новая таблица должна быть независимой. Допускаются встроенные простые поля, без ссылок, дополнительных индексов, ограничений кроме первичного ключа, пользовательских менеджеров и значений по умолчанию. Обработчики `pre_migrate` и `post_migrate` на этом пути не запускаются. Если релизу нужны создаваемые такими обработчиками разрешения, данные или другая инициализация, он требует ручного плана.

Старый worker продолжает обращаться к прежним таблицам. SQLite сериализует пишущие транзакции. На автоматическом пути `BEGIN IMMEDIATE` защищает повторное сравнение схемы и плана, создание таблицы и запись в `django_migrations`. Время ожидания SQLite при конфликте блокировок ограничено 5 секундами, сам автоматический этап миграции ограничен 30 секундами. При ошибке workflow останавливается. Записи, сделанные после online backup, могут отсутствовать в снимке, поэтому автоматического восстановления нет.

## Ручное окно для остальных миграций

`RunPython`, `RunSQL`, перестройки и прочие операции вне допуска требуют ручного запуска. Для неизвестной миграции до репетиции владелец должен проверить весь код и подтвердить, что он работает только с временной SQLite. Scratch использует существующий серверный аккаунт и настройки. Это не изоляция от сети и файлов сайта. Если миграция обращается к рабочим файлам или внешним сервисам, сначала перепишите её или испытайте в отдельном окружении. Затем для конкретного SHA используйте приватный файл `~/.mini-crm-deploy/allow-migrations` с правами `0600`. Автоматический запуск этот файл игнорирует.

**PR #188.** Обе известные версии миграции истории цен допускаются к штатной репетиции по SHA-256 файлов. Проверяется исходная строка для каждого объекта и наличие обоих триггеров. В рабочей БД миграция остаётся ручной. Она делает backfill и создаёт внешнюю связь. Старый worker, который ещё не знает модели истории, может при удалении объекта получить ошибку внешнего ключа. Backfill и DDL также удерживают SQLite write lock. Генерализации допуска на произвольный SQL нет.

Перед ручным apply:

1. Выключите `PA_AUTO_DEPLOY`. Назначьте окно работ и согласуйте SHA. Прогоните миграцию на приватной копии. Используйте `allow-migrations` для репетиции неизвестного SQL или Python только после ревью. Файл подтверждает решение и сам запросы не блокирует.
2. Остановите фоновые задания, импорты, ручные команды и другие источники записи. Для веб-трафика нужен проверяемый барьер до запуска apply. Например, оператор может временно установить внешнюю WSGI-обёртку, которая отвечает 503 на все маршруты, кроме read-only `/healthz/`. Выполните reload **до миграции**, убедитесь, что старые workers и запросы завершились, безопасными GET проверьте 503 на рабочих маршрутах и подтвердите, что фоновых писателей нет. Изменение в новом коде или файл-флаг без предварительного reload старых workers не останавливает. Если нет способа подтвердить остановку всех писателей, apply отложите.
3. В приватном файле `allow-migrations` оставьте полный согласованный SHA, затем запустите ручной `apply`. Держите барьер до успешных reload, health check и ack. После успеха снимите барьер, верните штатную WSGI-конфигурацию, сделайте reload, подтвердите SHA и только затем возобновите фоновые задания. Уберите допуск для завершённого SHA.
4. При ошибке оставьте записи остановленными до выбора восстановления. Проверьте `pending`, checkout и рабочую схему. Вернуть трафик можно после подтверждения совместимой пары кода и БД по инструкции ниже. При сбое до изменения рабочей схемы и checkout можно вернуть прежнюю штатную WSGI-конфигурацию и проверить прежний SHA.

## Диагностика и восстановление

В GitHub Actions сохранён `pa-deploy.log` со стадиями и номером запуска. На сервере полные журналы находятся в `~/.mini-crm-deploy/<run>.<mode>.log`, а SQLite-снимок перед изменениями в `~/.mini-crm-deploy/<run>.sqlite3`. Журналы и снимки могут содержать рабочие данные. Держите их приватными и управляйте сроком хранения с учётом дисковой квоты. Статус `pending` блокирует следующий apply до успешного подтверждения или ручного восстановления.

1. Выключите `PA_AUTO_DEPLOY`. При таймауте или ошибке сети сначала проверьте `pending`, журналы, Git HEAD, состояние рабочего процесса и блокировку. Команда могла продолжить выполнение после потери связи. При нарушении совместимости остановите записи. Снимите отдельную штатную SQLite-копию текущей БД, сохраните оба SHA и журналы.
2. Если рабочий SHA верен и проблема была только в наблюдении, после подтверждения `/healthz/` и SHA оператор может выполнить установленный `deploy-v2 ack <sha> <run>`. Он принимает подтверждение только для соответствующего статуса `ready`.
3. Для отката кода проверьте совместимость текущей схемы с `last-good`. При остановленных записях и чистом дереве сохраните ссылку на неудачный HEAD, затем вручную переключитесь на проверенный `last-good` через `git switch --detach --no-overwrite-ignore <last-good>`. Проверьте окружение, пересоберите локальную статику, сделайте reload и повторите health check. После проверки вручную верните локальную ветку `production` к подтверждённому SHA. Сохраните диагностику и снимки до снятия `pending`.
4. При несовместимой схеме проверьте возможность исправления вперёд или обратимости миграций на отдельной копии. Если требуется восстановление снимка, сначала сравните его с текущей сохранённой БД, выделите записи после снимка и согласуйте перенос или допустимое окно потери данных. Проверьте целостность восстановленной копии и совместимость кода, затем переключайте рабочий файл SQLite только при остановленных процессах и после согласования. Скрипт БД автоматически не восстанавливает. Объекты в Yandex Object Storage в SQLite-снимок не входят.

## Ограничения Free

Документированного способа запускать Bash по push с нуля на актуальном Free-тарифе нет. API может создать объект консоли, но запуск процесса требует браузера. Хостинг может перезапустить существующую консоль. SSH и Always-on Tasks доступны на платных аккаунтах. У аккаунтов, созданных до 15 января 2026 года (8 января в EU), может быть одна задача в сутки. Она запускается по расписанию, поэтому не заменяет запуск по push. На Free также действуют дисковая и CPU квоты, ограничения исходящих соединений и срок действия веб-приложения. При недоступной консоли нужен оператор. Публичного endpoint выполнения команд нет.

## Локальные проверки

```bash
bash -n deploy/deploy
python -m unittest discover -s deploy -p 'test_*.py'
```

API и health check в тестах подменены. SQLite-тесты используют временные локальные файлы. Dry-run не делает reload. Production reload и полный live-deploy пока не проверены.

Для проверки конкретного кандидата PR #188 на обеих цепочках передайте доступный локально проверенный SHA:

```bash
PA_PRICE_HISTORY_TEST_REF=d1a5146521cc0e5de3c7fe4f5fd32389f2778c2f \
  python -m unittest deploy.test_pa_price_migration
```

Тест создаёт две временные SQLite, проверяет backfill, фиксацию параллельной записи, откат и поведение писателя, который не знает о новой связи. Без локального SHA этот сценарий пропускается. Остальные тесты используют только текущий checkout.
