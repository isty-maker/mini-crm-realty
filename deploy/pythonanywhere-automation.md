# Автоматический деплой на PythonAnywhere Free

GitHub Actions использует уже запущенную выделенную Bash-консоль. Ручной запуск с `main` всегда выполняет dry-run. Автоматический запуск выключен по умолчанию. После включения workflow принимает только успешное завершение существующего `CI` для события `push` в `main` этого репозитория. Это включает push, созданный merge PR. Проверки PR сами по себе деплой не запускают. Checkout GitHub Actions и сервер должны подтвердить один и тот же полный SHA. Если `main` успел продвинуться до серверного fetch, устаревший запуск остановится.

## Перед настройкой

1. Сохраните как исходное рабочее состояние production на `bf6164eb52efacaa8eaaff6174c6e348778db049`. Сверьте фактический HEAD, локальные файлы миграций, активный `MIGRATION_MODULES` и применённые записи в `django_migrations`. Три серверные миграции требуют отдельного согласования. Сохраните их файлы и согласуйте их граф и фактическую схему на изолированной копии БД. Два исправления из PR #184 также требуют отдельного решения. Целевой `main` должен содержать сам коммит `bf6164e` в истории. Squash или rebase этих исправлений даст другой SHA и не пройдёт проверку предка.
2. Только после согласования настройте локальную ветку `production` на сервере из проверенного рабочего HEAD без перемещения файлов. Если ветки ещё нет, используйте `git switch -c production`. Проверьте чистый Git, включая неигнорируемые файлы, и origin `https://github.com/isty-maker/mini-crm-realty.git`. При необходимости внесите `/.env`, `/db.sqlite3-wal`, `/db.sqlite3-shm` и `/db.sqlite3-journal` в локальный `.git/info/exclude`. Дополнительные миграции должны пройти согласование, прежде чем дерево можно считать чистым.
3. На вкладке Web проверьте source directory `/home/isty/mini-crm-realty`, virtualenv `/home/isty/mini-crm-realty/venv`, Python 3.12 (наблюдаемая версия 3.12.8) и локальное отображение `/static/` на `/home/isty/mini-crm-realty/staticfiles`. Скрипт допускает обновления патч-версии Python 3.12. Сохраните действующую конфигурацию WSGI и загрузку окружения. В WSGI после настройки пути и окружения импортируйте `from realcrm.wsgi import application`. Этот модуль запоминает SHA при запуске рабочего процесса и отдаёт его в заголовке `X-App-Revision` на `/healthz/`. Сам URL по-прежнему возвращает `ok`.
4. Проверьте, что приватный `/home/isty/mini-crm-realty/.env` имеет права `0600`, а параметры приложения совпадают с WSGI. Для серверных команд нужны `DEBUG=False`, домен в `ALLOWED_HOSTS`, `https://isty.pythonanywhere.com` в `CSRF_TRUSTED_ORIGINS`, действующие переменные `YANDEX_CLIENT_KEY_ID`, `YANDEX_CLIENT_SECRET_KEY`, `YANDEX_STORAGE_BUCKET_NAME` и тот же режим миграций, что у рабочего сайта. Переменные в окружении консоли имеют приоритет над `.env`. Проверьте предупреждения `check --deploy`, включая настройки Django secret key и HTTPS, до включения автоматического режима. Проверки не обращаются к рабочим объектам Yandex.
5. Установите отдельно проверенную копию `deploy/deploy` из принятого коммита в `/home/isty/.mini-crm-deploy/deploy`. Подготовьте файл из проверенного checkout или передайте его через Files. GitHub Actions вызывает только этот установленный launcher. Обновление launcher выполняет оператор после ревью. Инициализируйте `last-good` **только при первоначальной настройке** значением проверенного SHA рабочего сайта. Сверьте его с HEAD. Пример команд для оператора после подготовки файла:

   ```bash
   umask 077
   install -d -m 700 "$HOME/.mini-crm-deploy"
   install -m 700 /path/to/reviewed/deploy "$HOME/.mini-crm-deploy/deploy"
   set -o noclobber
   printf '%s\n' bf6164eb52efacaa8eaaff6174c6e348778db049 > "$HOME/.mini-crm-deploy/last-good"
   set +o noclobber
   ```

6. Откройте выделенную Bash-консоль через Dashboard и оставьте её на свободном приглашении оболочки. Запишите фактический ID. Ранее использовалась консоль `42628336`. После перезапуска проверьте ID заново. Используйте только эту консоль для деплоя. Интерактивная команда, другой shell или длинный prompt могут помешать обмену.
7. Создайте GitHub Environment `production`, ограничьте deployment branches веткой `main`, если настройка доступна, и защитите `main` ревью и обязательным CI. Задайте в environment секрет `PA_API_TOKEN`, variables `PA_USERNAME=isty` и `PA_CONSOLE_ID`. Оставьте **repository variable** `PA_AUTO_DEPLOY` отсутствующей или со значением `false`. С токеном обращайтесь как с учётными данными аккаунта. Клиент передаёт его только официальному API, без HTTP-переадресаций.

## Ручная проверка и включение

- После попадания workflow и согласованного состояния в `main` запустите **Deploy to PythonAnywhere → Run workflow → main**. Dry-run проверяет настройки и активность Bash, получает точный tip `main`, распаковывает его в приватный временный каталог и проверяет установленные зависимости без их обновления. Django проверяет граф миграций и статику на временном SQLite-снимке. Рабочая БД открывается SQLite в режиме чтения. Dry-run не переключает checkout, не применяет миграции и не вызывает reload.
- При `412` откройте консоль в Dashboard, проверьте свободное приглашение и повторите dry-run. Ответ на POST лишь подтверждает приём ввода. Клиент ждёт отдельную строку с уникальным номером запуска и кодом выхода. Консоль показывает примерно последние 500 символов, поэтому подробности пишутся на сервере в приватный лог, а не в терминал. Ни один POST не повторяется автоматически.
- Проверьте dry-run и проведите проверку официального reload и `/healthz/` с ожидаемым SHA в согласованное окно. Локальные тесты с моками не подтверждают, что reload доступен этому рабочему сайту. Перед первым apply убедитесь, что хватает свободного места для исходников и SQLite-снимка, а также CPU на проверку и сбор статики.
- После явного разрешения установите `PA_AUTO_DEPLOY=true`. Успешный серверный apply сохраняет снимок SQLite, делает fast-forward, повторяет сверку плана на рабочей БД, собирает локальную статику и выполняет Django check. Workflow вызывает официальный reload, ждёт HTTP 200 с `ok` и SHA рабочего процесса и только затем подтверждает серверу завершение.
- Если есть план миграций, apply остановится до обновления checkout, пока оператор не проверит миграции на копии и не приостановит записи в CRM и фоновых задачах. Для конкретного проверенного SHA оператор записывает полный SHA в приватный `~/.mini-crm-deploy/allow-migrations` перед запуском apply. Продолжайте блокировать записи до успешных reload и health check. Для нового SHA требуется новое разрешение. При изменении зависимостей заранее подготовьте и проверьте совместимый virtualenv. Скрипт проверяет установленные версии через pip, но не изменяет рабочий virtualenv.

## Диагностика и восстановление

В GitHub Actions сохранён `pa-deploy.log` со стадиями и номером запуска. На сервере полные журналы находятся в `~/.mini-crm-deploy/<run>.<mode>.log`, а SQLite-снимок перед изменениями в `~/.mini-crm-deploy/<run>.sqlite3`. Журналы и снимки могут содержать рабочие данные. Держите их приватными и управляйте сроком хранения с учётом дисковой квоты. Статус `pending` блокирует следующий apply до успешного подтверждения или ручного восстановления.

1. Выключите `PA_AUTO_DEPLOY`. При таймауте или ошибке сети сначала проверьте `pending`, журналы, Git HEAD, состояние рабочего процесса и блокировку. Команда могла продолжить выполнение после потери связи. При нарушении совместимости остановите записи. Снимите отдельную штатную SQLite-копию текущей БД, сохраните оба SHA и журналы.
2. Если рабочий SHA верен и проблема была только в наблюдении, после подтверждения `/healthz/` и SHA оператор может выполнить установленный launcher с `ack <sha> <run>`. Он принимает подтверждение только для соответствующего статуса `ready`.
3. Для отката кода проверьте совместимость текущей схемы с `last-good`. При остановленных записях и чистом дереве сохраните ссылку на неудачный HEAD, затем вручную переключитесь на проверенный `last-good` через `git switch --detach --no-overwrite-ignore <last-good>`. Проверьте окружение, пересоберите локальную статику, сделайте reload и повторите health check. После проверки вручную верните локальную ветку `production` к подтверждённому SHA. Сохраните диагностику и снимки до снятия `pending`.
4. При несовместимой схеме проверьте возможность исправления вперёд или обратимости миграций на отдельной копии. Если требуется восстановление снимка, сначала сравните его с текущей сохранённой БД, выделите записи после снимка и согласуйте перенос или допустимое окно потери данных. Проверьте целостность восстановленной копии и совместимость кода, затем переключайте рабочий файл SQLite только при остановленных процессах и после согласования. Скрипт БД автоматически не восстанавливает. Объекты в Yandex Object Storage в SQLite-снимок не входят.

## Ограничения Free

Документированного способа запускать Bash по push с нуля на актуальном Free-тарифе нет. API может создать объект консоли, но запуск процесса требует браузера. Хостинг может перезапустить существующую консоль. SSH и Always-on Tasks доступны на платных аккаунтах. У аккаунтов, созданных до 15 января 2026 года (8 января в EU), может быть одна задача в сутки. Она запускается по расписанию, поэтому не заменяет запуск по push. На Free также действуют дисковая и CPU квоты, ограничения исходящих соединений и срок действия веб-приложения. При недоступной консоли нужен оператор. Публичного endpoint выполнения команд нет.
