# План развития CRM

1. **Карточка на существующих данных.** Публичные характеристики, цена, галерея, действующая планировка, выгрузки и история цены. Версии защищают сохранения карточки и полного редактора. Новое редактирование и дополнительно выводимые приватные поля доступны только сотрудникам. Синтетический макет целевой карточки существует отдельно, рабочий маршрут для него отсутствует.
2. **Вход сотрудников.** Перед включением нового редактирования на рабочем сайте проверить доступ ко всем маршрутам панели, фото, диагностике, будущим API и документам. Инвентаризировать скрипты и потребителей XML. Сохранить согласованные публичные фиды, проверки доступности и маршруты публичных изображений. Подготовить выдачу учётных записей и путь восстановления доступа. CSRF остаётся обязательным для браузерных изменений.
3. **Сохраняемые рабочие данные.** Ввести независимые рабочие статусы, условия, юридические свойства, типы и готовность документов и заметки. Новые приватные поля включать только после проверки авторизации. Применить миграции в обеих поддерживаемых цепочках сначала к пустой БД и синтетической копии со старыми записями. Сверить существующие значения, цены, историю, настройки экспорта и порядок фото. Для старых объектов сохранять неизвестные состояния, не интерпретировать архив как продажу. Перед rollout взять штатную копию SQLite и для несовместимых изменений остановить записи по инструкции деплоя. При откате не заменять рабочую БД поверх новых записей.
4. **Интеграции.** Read-only Google Drive и привязка планировки, импорт паспорта с конфликтами, авторизованный API и журнал, затем чтение статусов Авито после проверки доступных прав.
5. **Рабочие процессы.** Показы, события, задачи, договоры, расходы. Независимый статус в общем списке и фильтрация.

Источники требований: [назначение и интерфейс](CRM_PRODUCT_SPEC.md), [семантика](CRM_DATA_MODEL.md), [интеграции](CRM_INTEGRATIONS.md), [деплой](../deploy/pythonanywhere-automation.md).

## Checklist оператора для поэтапного выпуска

План относится к будущим действиям владельца. Сохраняйте отдельный релиз каждого PR. Автодеплой реагирует на успешный CI для push в main. До первого merge установите `PA_AUTO_DEPLOY=false` и дождитесь окончания уже запущенных работ. Убедитесь, что production имеет подтверждённый `last-good`, нет `pending`, есть доступ к закрытой консоли и место под временные SQLite.

| Этап | Что выпускается | Условие перехода |
|---|---|---|
| #192 | Карточка и защищённые секции. Новых миграций нет. | Сверить внешний клиент на копии по [контракту старых форм](CRM_HTTP_TRANSITION.md). После выпуска проверить прежний POST, обе XML-выгрузки и историю цены. |
| #193 | `crm_access/0001_initial`, `0002_invitation_client_throttle`. | В рабочем окружении оставить `CRM_REQUIRE_STAFF_LOGIN=false`, пока клиенты зависят от старых форм. На копии проверить обратный прокси, HTTPS, отсутствие DEBUG, Secure-cookie, индивидуальное приглашение, резервный вход, logout и публичные mappings. |
| #194 | Стандартная цепочка `core/0015`–`0018`. Альтернативная `core/0003`–`0008`, где 0007–0008 выравнивают старые колонки карточки и фото. | Проверить архивирование, приватные маршруты и оба фида. На пустой и заполненной копиях прогнать обе цепочки. В production использовать только уже действующую цепочку. Для альтернативной дополнительно сверить ID и порядок фото, историю, наличие обоих триггеров цены и не допустить открытого рабочего доступа к паспортам. |
| #195 | `crm_api/0001_initial`, `0002_scope_listing_identifiers`. | Верифицировать на копии dry-run, повторное заполнение, запись через версию, отзыв ключа и существующие HTTP-клиенты. Ключи, существовавшие до 0002, требуют перевыпуска. |

Для каждого этапа заново получите полный хеш **результирующего коммита main** после согласованного merge. Проверьте зелёный push CI именно этого SHA. Для #193–#195 действует ручной процесс deploy-v2. Просмотрите операции миграции и выполните репетицию на приватной копии. В `~/.mini-crm-deploy/allow-migrations` с правами 0600 согласуйте только этот полный SHA. Выполните ручной `dry-run`; перед `apply` остановите фоновую запись и подтвердите рабочий барьер для прежних WSGI workers. Держите барьер до проверки `/healthz/`, ревизии, reload и ack. Затем проверьте сайт на ожидаемом SHA, уберите допуск и возобновите работу. Автоматический режим не использует allow-файл и сложные миграции не применяет.

Если рабочие клиенты ждут API, включайте обязательный вход **после #195** в отдельном согласованном окне. До смены флага проверьте новую цепочку на копии, подготовьте резервный вход и программный клиент, проверьте секрет и HTTPS/static mappings. При переключении сначала остановите старые импорты, включите флаг и проверьте вход, закрытие панели, работу ограниченного API, оба XML и фото. Потом возобновите запись через авторизованный клиент. Если владелец проверил авторизованную HTML-замену раньше, допускается отдельное окно включения между #193 и #194. Без проверенной замены рабочий переход откладывается.

До миграции сделайте штатный SQLite backup, запишите SHA, цепочку и отметку времени и проверьте целостность снимка. При сбое оставьте запись остановленной, проверьте `pending` и снимите дополнительную копию текущей БД. Откат кода к `last-good` допустим после проверки его совместимости со схемой. Для восстановления старого снимка сравните его с отдельной копией текущего состояния, сохраните или согласуйте перенос новых записей, проверьте целостность и выполните ручную замену только при остановленных процессах. Фото в Object Storage учитываются отдельно. [Инструкция PythonAnywhere](../deploy/pythonanywhere-automation.md)
