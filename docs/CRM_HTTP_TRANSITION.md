# Переход со старых HTTP-форм

Исходники внешних скриптов загрузки паспорта в этом репозитории не найдены. Тесты воспроизводят контракт Django, а совместимость конкретных клиентов требует прогона владельцем на копии.

До включения обязательного входа прежние POST `/panel/create/` и `/panel/edit/{id}/` принимают URL-encoded и multipart форму. Сначала GET того же маршрута, затем POST с той же cookie и CSRF через `csrfmiddlewaretoken` либо заголовок `X-CSRFToken`. Создание требует обязательных полей полного редактора. Для квартиры это категория, операция, подтип, общая площадь и валюта. У редактирования отсутствующее поле сохраняет значение. Для явного снятия checkbox передайте `false`, для установки `on`. В HTML перед checkbox отправляется скрытое `false`, последнее значение определяет состояние. Существующие поля кадастрового номера и номера квартиры остаются в старой форме и поддерживаются при POST, как до расширения карточки. Новая карточка ограничивает их показ сотрудниками.

Для редактирования передавайте `edit_version` из GET. В защищённом режиме он обязателен. До перехода его отсутствие у старого клиента допустимо, условная запись всё равно проверяет снимок внутри запроса. Такой клиент не защищён от устаревшего снимка между отдельными GET и POST. HTTP 302 означает сохранение, HTTP 200 при POST может означать ошибки формы, 409 означает конфликт. Не повторяйте конфликтующий запрос сформированными ранее данными. Прочитайте свежую версию, сопоставьте значения и подтвердите правку заново.

После включения доступа используйте браузерную сессию сотрудника с CSRF либо авторизованный API, когда он доступен. Не добавляйте исключения без входа для старых скриптов. До включения проверьте создание, частичный POST, фото, требуемые поля, флаги и редиректы каждого действующего клиента на изолированной БД. Сохраните публичные GET/HEAD XML и healthz. Текущие фиды могут включать предусмотренные прежней схемой кадастровый номер и номер квартиры. До рабочего выпуска нужно согласовать их с владельцем и потребителями фидов.

## Проверка конкретного клиента на копии

1. Запустите `python manage.py test core.tests.test_property_detail --noinput` для проверки серверного контракта. Для проверки своего клиента укажите URL изолированной копии, отдельную cookie jar и только синтетический адрес.
2. Получите GET создания. Сохраните cookie, CSRF и обязательные поля из формы. Отправьте multipart POST с тестовыми кадастровым номером и номером квартиры. Проверьте 302 и откройте указанный маршрутом редиректа редактор. Сверьте сохранённые значения.
3. Считайте свежий скрытый `edit_version`. Измените одно поле, опустив остальные, и проверьте их сохранность. Затем новым POST явно снимите включённый флаг (`false`) и очистите необязательный номер квартиры пустой строкой. Проверьте, что второй флаг и посторонние поля сохранились.
4. Отправьте пустую обязательную площадь с корректными CSRF и версией. Убедитесь, что HTTP 200 содержит ошибку формы, а GET показывает прежнюю площадь. Проверьте 403 без CSRF и 409 для старой версии после отдельной правки. В защищённом режиме проверьте также отказ без версии.
5. Сравните итоговые XML на копии. Зафиксируйте результаты для каждого внешнего клиента до переключения. Не переносите cookie и данные копии в рабочую CRM.
