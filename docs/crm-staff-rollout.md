# Включение входа сотрудников

Сначала на изолированной копии проверьте новые маршруты, выдайте индивидуальные учётные записи Django с правом staff и подготовьте случайный `DJANGO_SECRET_KEY` вне репозитория. В рабочем окружении должен использоваться HTTPS. Включите `CRM_REQUIRE_STAFF_LOGIN=true` только после проверки учётной записи, HTTPS и резервного доступа оператора. При включённой политике настройки требуют ключ минимум из 50 символов. Смена ключа завершит действующие сессии.

После согласованного reload проверьте вход, выход, 403 при POST без сотрудника и отсутствие кэширования приватных ответов. Проверьте анонимный GET/HEAD для `/healthz/`, обеих XML-выгрузок и всех публичных изображений, используемых фидами. Публичные фиды сохраняют согласованные поля. Для остальных скриптов зафиксируйте владельца, используемый маршрут и способ доступа. CLI-команды Django не требуют веб-сессии. При необходимости сначала перенесите старую HTTP-диагностику на доступ оператора по консоли.

PythonAnywhere может обслуживать статические файлы вне Django. Проверьте его mappings отдельно. Публичные фото, которые нужны XML, должны остаться доступны. Каталоги логов, временные файлы, SQLite, резервные копии, документы и приватный кэш не должны попадать в публичные mappings. Удалите доступные публикации этих каталогов после проверки зависимых скриптов. Эти настройки в репозитории не меняются.

До завершения проверки владельцем политика rollout остаётся выключенной. Добавление приватных рабочих данных требует включённой политики и отдельной проверки допуска.
