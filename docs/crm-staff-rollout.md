# Включение входа сотрудников

Сначала на изолированной копии проверьте новые маршруты, выдайте индивидуальные учётные записи Django с правом staff и подготовьте случайный `DJANGO_SECRET_KEY` вне репозитория. В рабочем окружении должен использоваться HTTPS. Включите `CRM_REQUIRE_STAFF_LOGIN=true` только после проверки учётной записи, HTTPS и резервного доступа оператора. При включённой политике настройки требуют ключ минимум из 50 символов. Смена ключа завершит действующие сессии.

После согласованного reload проверьте вход, выход, 403 при POST без сотрудника и отсутствие кэширования приватных ответов. Проверьте анонимный GET/HEAD для `/healthz/`, обеих XML-выгрузок и всех публичных изображений, используемых фидами. Публичные фиды сохраняют согласованные поля. Для остальных скриптов зафиксируйте владельца, используемый маршрут и способ доступа. CLI-команды Django не требуют веб-сессии. При необходимости сначала перенесите старую HTTP-диагностику на доступ оператора по консоли.

PythonAnywhere может обслуживать статические файлы вне Django. Проверьте его mappings отдельно. Публичные фото, которые нужны XML, должны остаться доступны. Каталоги логов, временные файлы, SQLite, резервные копии, документы и приватный кэш не должны попадать в публичные mappings. Удалите доступные публикации этих каталогов после проверки зависимых скриптов. Эти настройки в репозитории не меняются.

До завершения проверки владельцем политика rollout остаётся выключенной. Добавление приватных рабочих данных требует включённой политики и отдельной проверки допуска.

## Приглашения и переход

Вместо пароля сотрудник открывает персональное приглашение и подтверждает вход. Подготовьте активную учётную запись Django с флагом staff. Из закрытой операторской консоли вызовите `python manage.py crm_invite <сотрудник> --origin https://<хост> --hours 24`. Команда выводит ссылку один раз. Передайте её сотруднику по закрытому каналу. Не сохраняйте вывод в CI, общем терминале, тикете или журнале. Токен находится во фрагменте ссылки и переходит только в тело HTTPS POST с CSRF. GET мессенджера приглашение не тратит. В базе хранится только хеш. Подтверждение одноразовое. База ограничивает число попыток до 12 в минуту на сетевой адрес WSGI и до 600 в минуту на установку. Заголовок X-Forwarded-For игнорируется. За прокси проверьте REMOTE_ADDR на копии. Если хостинг передаёт общий адрес, сотрудники делят лимит; повторите вход через минуту и сохраните доступ через закрытую операторскую консоль. Глобальный предел всё ещё может сработать при распределённом трафике.

`python manage.py crm_invite <сотрудник> --revoke <id>` отзывает неиспользованную ссылку. `--disable` деактивирует сотрудника, завершает возможность использовать ранее выданные сессии и отзывает ожидающие приглашения. Для восстановления владелец через резервную консоль активирует свою учётную запись и выдаёт новое приглашение. Срок сессии задаёт `CRM_STAFF_SESSION_DAYS` от 1 до 180, по умолчанию 90. Старые браузерные сессии не возобновятся при активации. Для программных клиентов требуется отдельная выдача новых ключей. Защищённый режим отклоняет DEBUG=True при загрузке и требует HTTPS и cookies Secure, HttpOnly и SameSite.

Если TLS заканчивается на прокси, подтвердите, что хостинг перезаписывает `X-Forwarded-Proto` и пользователь не может подделать доверенный заголовок. Только после этого включайте `CRM_TRUST_PROXY_HTTPS=1`, если Django иначе не видит HTTPS. При ошибке входа сохраняйте операторскую консоль и диагностируйте на копии. Временно возвращать прежний режим можно только пока новые приватные данные остаются закрытыми. Откат кода не требует стирать сессии или менять рабочую БД.

Переходный режим описан в [контракте старых форм](CRM_HTTP_TRANSITION.md). После включения входа исключений для старых скриптов нет. Ускоренные записи и полный редактор требуют версии, а HTML-запросы также требуют сессии и CSRF. Подготовьте авторизованную замену до переключения флага.

Если авторизованный клиент ещё зависит от API, держите переходный режим до выпуска всей цепочки. Заранее репетируйте включённую политику на копии. Переключайте рабочий режим в отдельном согласованном окне после миграций API и проверки резервного входа.
